# Datasets

## Purpose of this directory

All data used by the platform, organised by lifecycle stage.

## Why this directory exists

Data quality is the first priority in this project's philosophy, and for a
low-resource language it is the binding constraint on nearly everything
downstream. This directory is where that priority becomes concrete: it is
structured so that provenance, licensing, and processing lineage are visible
rather than implied.

## Structure

| Directory | Contents | Mutability |
| --- | --- | --- |
| `raw/` | Source data exactly as obtained. Never edited. | **Immutable** |
| `processed/` | Cleaned, normalised, transformed data. Produced only by scripts. | Regenerable |
| `evaluation/` | Held-out test sets. Never used for training or tuning. | **Sacred** |
| `dictionaries/` | Lexical resources, word lists, morphological lexicons. | Curated |
| `terminology/` | Domain terminology, glossaries, named entity lists. | Curated |

## The three rules that matter most

**1. Raw data is immutable.** Never edit anything in `raw/`. Transformations
produce new artefacts in `processed/`, generated by scripts in
`scripts/data_processing/`. If you cannot regenerate `processed/` from `raw/` by
running a script, the pipeline is broken.

**2. Evaluation data is never touched.** Nothing in `evaluation/` is used for
training, tuning, prompt development, or inspection during development. Once
evaluation data leaks into any of those, it is burned — and unlike most mistakes,
this one cannot be undone. It silently invalidates every result measured against
it thereafter.

**3. Licence and provenance are mandatory.** Every dataset documents where it came
from, under what licence, and what may be done with it. Undocumented data is
unusable data — we are building infrastructure others depend on, and we cannot
pass on rights we do not have (**P-9**, **A-009**).

## Required documentation per dataset

Every dataset directory contains:

```
datasets/<stage>/<dataset-name>/
├── README.md              What it is, why we have it, known limitations
├── PROVENANCE.md          Where it came from, how, when, by whom
├── LICENSE                The actual licence text
└── <name>.manifest.json   File list, sizes, checksums, record counts
```

A dataset without these is not usable and should not be built on.

### `PROVENANCE.md` must answer

- Original source, with URL and access date
- Collection method
- Licence and what it permits
- Consent basis, where data is human-sourced
- Any known restrictions on use or redistribution
- Processing applied, and by which script at which commit
- Known quality issues, gaps, and biases

## What is tracked in git

**Tracked:** READMEs, provenance records, licences, manifests, small structured
metadata.

**Not tracked:** the data itself. See `.gitignore`. Large files do not belong in
git — commit a documented retrieval script instead, until a storage decision is
recorded in `docs/decisions/DECISIONS.md`.

## Naming

`<source>-<content>-<version>/` — e.g. `wikipedia-ti-dump-2026-07/`,
`parallel-ti-en-v1/`

## What future contributors should add

Datasets, fully documented. Also record datasets that were **evaluated and
rejected**, with the reason — in `docs/research/references/datasets.md`. "Found,
but licence prohibits derivative works" is exactly the kind of finding that saves
the next person a day.
